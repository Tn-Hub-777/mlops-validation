# MLOps Validation, Training, Testing and Model Delivery

## 1. Project overview

This repository implements a fail-closed machine-learning pipeline:

1. Download and validate the dataset.
2. Create a reproducible train/validation split.
3. Train a `DummyClassifier` baseline.
4. Train a candidate `RandomForestClassifier`.
5. Evaluate both with the same validation data and metric.
6. Stop with a non-zero exit code if the quality gate fails.
7. Run application tests in the same GitHub Actions job.
8. Publish a downloadable model package only after every required check passes.

No notebook, Colab runtime, mounted Google Drive, GCP deployment, Docker image, or live API is required.

## 2. Dataset and task

**Dataset:** UCI Banknote Authentication

**Source:** UCI Machine Learning Repository  
Stable download URL used by the code:

`https://archive.ics.uci.edu/static/public/267/banknote+authentication.zip`

The dataset is downloaded automatically at workflow/runtime execution and does not require authentication.

**Target variable:** `class`

**Input features:**
- `variance`
- `skewness`
- `curtosis`
- `entropy`

**Prediction task:** binary classification of whether a banknote observation is authentic or forged.

The dataset is small, tabular, numeric, and suitable for a CPU-only training workflow.

## 3. Evaluation metric

The primary metric is **balanced accuracy**.

Balanced accuracy is the average recall across the classes. It is appropriate for a binary classification task because it gives each class equal importance rather than allowing the majority class to dominate ordinary accuracy.

The same metric is used for both the DummyClassifier baseline and the candidate model on exactly the same validation set.

## 4. Reproducibility and preprocessing

The split is:

- 80% training
- 20% validation
- `random_state=42`
- stratified by the target

The candidate uses `StandardScaler` inside a scikit-learn `Pipeline`. The scaler is fitted only as part of the pipeline's training fit, so validation data is not used to fit preprocessing.

The Random Forest uses `random_state=42`.

## 5. Quality gate

Balanced accuracy is a higher-is-better metric.

The required rule is:

`model score >= baseline score + margin`

The margin is **0.05 balanced-accuracy points**.

Therefore, if the baseline is 0.5000, a candidate must reach at least 0.5500.

### Why 0.05?

A 0.05 absolute improvement is large enough to require a meaningful improvement over the trivial baseline while remaining achievable for a small tabular classification problem.

If the margin were too low, a model could pass despite providing only a negligible improvement. If it were too high, a useful model could be rejected because the gate demands an unrealistic improvement.

The metric, split and margin must remain unchanged during the failure/recovery demonstrations.

## 6. Validation checks

`src/data.py` rejects the dataset when:

- a required feature is missing;
- the target is missing;
- missing values are present;
- the dataset is unexpectedly small.

`src/train.py` exits with code 1 when:

- dataset validation fails;
- training/evaluation raises an exception;
- the candidate fails the quality gate.

A printed failure message alone is therefore not sufficient to pass a CI step.

## 7. Application tests

`tests/test_application.py` verifies:

1. The saved model can be loaded.
2. A valid sample produces one prediction with the expected shape.
3. The prediction function accepts a valid sample.
4. A sample missing a required feature is rejected with a clear `ValueError`.

Training and testing run in the **same GitHub Actions job**, so the tests use the model generated by that workflow run.

## 8. GitHub Actions pipeline

Workflow:

`.github/workflows/mlops.yml`

The workflow runs on pushes to `main`.

Stages in the same job:

```text
Push to main
    |
    v
Checkout repository
    |
    v
Set up Python
    |
    v
Install dependencies
    |
    v
Validate dataset
    |
    v
Train baseline + candidate
    |
    v
Quality gate
    |
    +---- FAIL ---> Job fails ---> No artifact publication
    |
    v
Application tests
    |
    +---- FAIL ---> Job fails ---> No artifact publication
    |
    v
Build model package
    |
    v
Upload GitHub Actions artifact
```

The upload step has no `continue-on-error` and is reached only if all previous steps succeed.

## 9. Model package

The successful workflow publishes an artifact named:

`model-package-run-<WORKFLOW_RUN_NUMBER>`

It contains:

- `model.joblib` — trained model including fitted preprocessing
- `metrics.json` — baseline, candidate, margin, required score and gate result
- `predict.py` — prediction application
- `requirements.txt` — dependencies
- `README.md` — project documentation
- `BUILD_INFO.txt` — workflow run identifier

The artifact is identified by the GitHub Actions workflow run number.

**Important:** download the successful artifact before its GitHub Actions retention period expires and keep a local copy for submission evidence.

## 10. Failure and recovery demonstration

The gate, metric, split and margin are not changed during the demonstrations.

### Failure A — model quality failure

For the quality-failure run, temporarily change the candidate training code so that it trains on a deliberately tiny subset of the training data while evaluating on the unchanged validation set.

For example, immediately before `candidate.fit(...)`:

```python
candidate.fit(X_train.iloc[:10], y_train.iloc[:10])
```

Push this change to `main`.

Expected result:

- data validation passes;
- candidate training completes;
- the candidate fails the existing quality gate;
- `src/train.py` exits with code 1;
- the GitHub Actions job stops;
- the package upload step is never reached;
- no model package is published.

## 11. Brief MLOps maturity assessment

This implementation is best described as an **early CI/CD-oriented MLOps implementation**.

It demonstrates:

- automated dataset validation;
- reproducible training;
- baseline comparison;
- an explicit model-quality gate;
- automated application tests;
- fail-closed artifact delivery;
- versioned workflow artifacts;
- repeatable execution independent of the developer environment.

It does not yet provide more advanced capabilities such as:

- experiment tracking;
- a model registry;
- automated model promotion between environments;
- production monitoring;
- data-drift/model-drift monitoring;
- scheduled retraining;
- deployed serving infrastructure;
- automated rollback.

Those capabilities would be needed for a more mature production MLOps system.

## 12. Local setup

Python 3.12 is recommended.

```bash
python -m venv .venv
```

Windows:

```bash
.venv\Scripts\activate
```

Linux/macOS:

```bash
source .venv/bin/activate
```

Install:

```bash
pip install -r requirements.txt
```

Validate data:

```bash
python -m scripts.validate_data
```

Train and evaluate:

```bash
python -m src.train --output-dir artifacts
```

Run tests after successful training:

```bash
python -m pytest -q
```

Run prediction:

```bash
python src/predict.py
```
